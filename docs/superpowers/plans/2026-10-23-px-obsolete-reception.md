# PX Obsolete Reception Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every PX reception explicitly `VIGENTE` or `OBSOLETO`, route all finalized equipment accordingly, and expose obsolete boxes in a dedicated sidebar warehouse.

**Architecture:** Persist a reception-level destination (`CENTRAL` or `OBSOLETE`) on `receptions`; the existing incremental PX capture remains the only creator of equipment. The start/join and finalize RPCs enforce destination consistency and atomically promote boxes/series to either central inventory or obsolete inventory. A read-only warehouse module lists `OBSOLETO` boxes through a server API.

**Tech Stack:** Next.js 16, React 19, TypeScript, Zod, Supabase/PostgreSQL, Vitest, Testing Library.

**Spec:** Conversation requirements dated 2026-10-23.

## Global Constraints

- Classification is mandatory when a PX reception starts.
- One reception cannot mix vigente and obsolete equipment.
- Classification cannot change after the first captured equipment.
- PX duplicate validation remains unchanged and global across S1-S4.
- Obsolete finalization writes `series.current_status = 'obsolete'` and `boxes.rack_location = 'OBSOLETO'`.
- Vigente finalization preserves `in_central_warehouse` and `BODEGA_CENTRAL`.
- Existing unrelated working-tree changes must not be overwritten.
